# 09 — Decision Log (ADRs)

> **Big Phase 2:** B-ADR-01..15 are summarised at the end of this log (full text in `docs/phase2/B08_DECISIONS.md`). ADR-005 is narrowed by B-ADR-03; ADR-022 is superseded as the primary deployment by B-ADR-04.

Each decision: context → decision → consequences. Status: `accepted` (Akshat approved), `proposed` (Claude Code added, awaiting approval), `superseded by ADR-x`. Append new ADRs at the end using the template. These entries double as viva answers to "why did you choose X?".

### ADR-001 India-only scope — accepted (Sep 2026)
**Context:** v1 planned US (SEC) + India. **Decision:** India only, RHPs of mainboard IPOs. **Consequences:** a sharper story (retail IPO investors, lakh/crore), one document type to parse well, a clear gap vs prior English/Korean financial-hallucination work.

### ADR-002 No hosted LLM APIs at runtime — accepted
**Context:** API wrappers are common and hard to defend as "our model". **Decision:** open-weight models only, run locally (Ollama) and on CPU when deployed. **Consequences:** smaller LLMs → we compensate with retrieval quality, strict prompts and the deterministic verifier. Frontier models appear only as a comparison baseline (E9).

### ADR-003 Distant supervision for the extractor — accepted
**Context:** no labelled RHP QA dataset exists; manual labelling thousands of examples is impossible solo. **Decision:** seed values from high-precision cover-page rules, propagate to other passages by normalized value match, train DeBERTa extractive QA (SQuAD 2.0 format). **Consequences:** label noise → measured by a 50-sample audit; the model can generalize to phrasings the rules miss.

### ADR-004 Deterministic numeric verifier — accepted
**Context:** NLI/LLM-judge faithfulness metrics are known to struggle on bare numbers. **Decision:** parse and compare numbers in code with explicit reason codes; scale mismatch is always ❌. **Consequences:** explainable, testable, near-100 % on scale errors; qualitative claims need a separate NLI check (P1).

### ADR-005 Never use rating labels; never advise — accepted
**Context:** the IPO dataset includes Apply/Avoid ratings; SEBI requires registration for advice. **Decision:** ignore rating labels entirely; advice guard refuses. **Consequences:** clean ethics section; no "prediction" feature.
**Phase 2 note:** narrowed by B-ADR-03 (proposed): outcome data may be used **only to validate** the risk level (E21), through `evaluate/outcomes.py`, never to train or tune anything.

### ADR-006 Timeline: single deadline 1 Nov, no 12 Oct demo — accepted (29 Sep 2026)
**Context:** the v2 plan was built around a 12 Oct presentation; that presentation is no longer required. **Decision:** one timeline to Sun 1 Nov with freeze on Mon 26 Oct; depth items (gold v2, BiLSTM-CRF, frontier comparison) move into the main plan. **Consequences:** stronger evaluation; gates G0–G5 in `07_ROADMAP.md`.

### ADR-007 Local first, deploy after stable — accepted
**Decision:** full product on the laptop by G4; a "lite" public deployment (Vercel + Hugging Face Space CPU) by G5. **Consequences:** `deploy_cpu` profile with smaller LLM; precomputed artifacts make most pages instant.

### ADR-008 Laptop constraints drive model sizes — accepted
**Context:** 16 GB RAM (~8 GB used by Windows + tools), RTX 2050 with 4 GB VRAM. **Decision:** LLM 2–4 B at 4-bit on GPU (bake-off decides), encoders as ONNX int8 on CPU online, lazy ASR, `dev_light` profile for daily coding, offline pipeline runs with Ollama stopped. **Consequences:** real measurements recorded in Phase 3.1 (new ADR).

### ADR-009 SQLite + FAISS + files, no database server — accepted
**Decision:** ≤ 50 IPOs fit easily; zero ops. Postgres/pgvector only if deployment needs it.

### ADR-010 Page images + word boxes instead of a PDF viewer — accepted
**Decision:** render pages to WebP and overlay boxes. **Consequences:** exact highlights, fast, identical behaviour on phones; no text selection in the viewer (acceptable).

### ADR-011 Windows-native tooling: uv + poethepoet + ruff — accepted
**Decision:** no Make, no WSL; ruff replaces black/isort/flake8. **Consequences:** same commands in Git Bash, PowerShell and CI.

### ADR-012 Rebase-merge PRs — accepted
**Decision:** keep every commit on `main` (see `08_GIT_WORKFLOW.md` §1). **Consequences:** history must stay clean → amend/rebase locally before pushing.

### ADR-013 Paid Colab is optional — accepted
**Context:** all P0/P1 training fits Kaggle's free GPUs; student AI Pro includes Colab units but only on paid plans. **Decision:** buy only if QLoRA (FR-34) is committed by ~20 Oct. **Consequences:** expected spend ₹0.

### ADR-014 Visual concept "tick and tie" — accepted
**Decision:** auditor's verification marks as the brand; stamp-ink blue accent; IBM Plex Sans + Plex Sans Devanagari. **Consequences:** a design rooted in the subject rather than a generic dark dashboard; see `03_UI_UX_DESIGN.md`.

### ADR-015 Cross-lingual retrieval, not translation — accepted
**Decision:** bge-m3 embeds Hindi questions and English passages into one space; the LLM answers in Hindi while copying numbers exactly. **Consequences:** no translation model; numbers in Hindi answers are verified the same way.

### ADR-023 Two documents per IPO: RHP and final Prospectus — proposed (30 Sep 2026)
**Context:** the downloaded RHPs leave the offer price, total issue size and the OFS rupee amount as `[●]`; the final Prospectus (filed after pricing) fills them in. Both exist for all 10 demo IPOs.
**Options:** (A) RHP only, show `[●]` as ⚠️ everywhere; (B) RHP + Prospectus parsed by the same pipeline; (C) also require the price-band advertisement.
**Decision:** B. Fields become `fresh_issue_size`, `ofs_shares` (count), `ofs_amount`, `offer_price`, `price_band` (optional; RHP or price-band ad if easy to find) and `total_issue_size`. Every value cites its document and PDF page; a `[●]` in the RHP is a normal ⚠️ and the Prospectus value is shown beside it as `companion`.
**Consequences:** `doc_type` on parsed docs, passages and candidates; two sets of page images; gold v1 records the document. `offer_price` is rules-only on the Prospectus cover and outside the QA ladder (no positives in RHP-derived training text). The Prospectus is the more authoritative source for final prices; chat retrieval indexes both, and answers say which document a figure came from.

### ADR-024 Contract-first API skeleton — proposed (30 Sep 2026)
**Context:** the frontend starts in Phase 1 but the real API arrives in Phase 4, and OpenAPI does not describe SSE event payloads by default.
**Decision:** P0.3 ships a FastAPI skeleton where every route in `06` returns 501 with its response model, and each SSE event is a pydantic model registered in OpenAPI. `poe gen-openapi` writes a committed `openapi.json` and the frontend generates types from it from F1 onward.
**Consequences:** shapes are agreed before either side is built; contract tests exist from the start; changing a shape means changing `06`, the model and `openapi.json` in one PR.

### ADR-025 Page numbering: PDF page primary, printed page secondary — proposed (30 Sep 2026)
**Context:** RHPs print their own page numbers, which differ from the PDF page index; an examiner opening the PDF would see a mismatch.
**Decision:** all page numbers in the API, viewer chips and citations are PDF pages (1-indexed). The printed page number is stored alongside and shown in the popover.
**Consequences:** `Page.printed_page` is read from the footer where present (nullable); "p. 12" in the UI always means the 12th PDF page.

### ADR-026 Dev/test split of the demo set; gold v1 labelled in Phase 1 — proposed (30 Sep 2026)
**Context:** writing rules and picking extractors on the same IPOs used for the reported ladder would leak test information; the original plan labelled gold after the X-Ray already existed.
**Decision:** 3 dev / 7 test IPOs. Rules, thresholds, prompts and per-field extractor choice are tuned on dev only; reported numbers use test. Gold v1 is labelled blind in Phase 1 (P1.7), before any extractor exists. Proposed dev set: `hexaware-technologies-2025` (pure OFS), `ather-energy-2025`, `urban-company-2025`; confirmed in P0.4.
**Consequences:** fewer test IPOs (7), so results are reported with bootstrap intervals and per-field numbers are descriptive (ADR-031). Gold v2 (10 more held-out IPOs) increases the test size later.

### ADR-027 Scale-mismatch requires a scale signal — proposed (30 Sep 2026)
**Context:** the rule "a 10/100/1000× difference is always a scale mismatch" also fires on genuinely different values, e.g. face value ₹10 vs ₹1.
**Decision:** `scale_mismatch` only when the ratio is 10ᵏ (k = 1–3) **and** (the scale words differ **or** the printed digits are identical). Any other 10ᵏ gap is `wrong_value`. Scale mismatch is always ❌.
**Consequences:** fewer mislabelled reasons in the evidence drawer; a unit test per case; the seeded-error harness includes a "10× wrong value" negative.

### ADR-028 Numeral policy for Hindi — proposed (30 Sep 2026)
**Context:** Hindi answers may write scale words as लाख/करोड़/हज़ार/अरब and currency as रुपये; documents could contain Devanagari digits.
**Decision:** the normalizer parses Hindi scale words, रुपये and Devanagari digits. Generated answers always use Western digits (0–9) and may use Hindi scale words. Devanagari digits are never output.
**Consequences:** ≥ 12 Hindi cases in the P1.4 table; Hindi answers are verified through the same path as English.

### ADR-029 Dependency groups; no torch in the API image or CI — proposed (30 Sep 2026)
**Context:** the online path uses ONNX int8 encoders, Ollama and CTranslate2, none of which need PyTorch; torch costs ~1 GB RAM and a large CI download.
**Decision:** uv dependency groups `api`, `ml` (torch, transformers, offline and Kaggle), `asr`, `dev`. CI installs `api` + `dev` only; the CUDA wheel is pinned under `ml`.
**Consequences:** faster CI, smaller deploy image, lower RAM; tests needing torch are marked `slow`.

### ADR-030 One primary package per sub-phase; capped `inspect` command — proposed (30 Sep 2026)
**Context:** the roadmap's sub-phases wire several packages (e.g. P2.2 touches extract, verify and pipeline), and Claude Code may not read PDFs or raw data yet must debug parsing.
**Decision:** rule reworded to one primary package per sub-phase with wiring elsewhere through `__init__.py`. `finsight.pipeline inspect` prints ≤ 40 lines and may write ≤ 30 truncated snippets to `data/samples/`.
**Consequences:** `CLAUDE.md` updated; debugging works from summaries, not source documents.

### ADR-031 Headline claim and ladder settings — proposed (30 Sep 2026)
**Context:** with 7 test IPOs one IPO moves a field's score by 10+ points; cover-page sentences are templated so rules read them almost perfectly.
**Decision:** the headline result is overall NVM with a bootstrap CI (by IPO) and a paired per-IPO comparison between rungs; per-field results are descriptive. Every ladder is reported for the **full document** and **body-only** (cover masked).
**Consequences:** the PRD target "better on ≥ 5 of 8 fields" is treated as a descriptive goal; the report states which claims the sample supports.

### ADR-016 Training corpus source — proposed (30 Sep 2026)
**Context:** `ingest.recon` on `sohomghosh/Indian_IPO_datasets` (public, CC BY-NC-SA 4.0), mainboard files only. The Excel has 418 IPOs (close years 2009-2023, 217 columns) and the text zip has 424 pagewise JSON texts (`Page_N` maps, median 440 pages, 3.9 MB). Answers to `05` section 1.2:
1. *Full text?* Yes: full pagewise text for every entry, but from mixed document kinds. File names lie: about 170 of the 219 files named `_RHP` have a cover titled PROSPECTUS. Judged by the first title phrase on the cover, the 424 texts are **112 RHP, 286 final Prospectus, 11 DRHP, 15 unknown** (unreadable font encoding or non-prospectus).
2. *Mainboard vs SME, years?* Only the mainboard files were downloaded (418 IPOs, 2009-2023; 62 closed in 2021, 57 in 2023). No IPO from 2024-2026.
3. *De-duplication against the demo set?* Company names are usable (`Issuer Company`, `Company Name`, `Close Year`). None of the 10 demo IPOs (all 2025) appears in the dataset; the exclusion test still runs.
The Excel's `Fresh Issue`, `Offer for Sale`, `Total Issue Size`, `Price Band`, `Final_Issue_Price` and `Face Value per share` columns are present (fresh issue 43 % and OFS 52 % populated; some hold `[.]` placeholders) and can cross-check seed values. Outcome, subscription, listing-day and broker/member columns are never read.
**Options:** (A) RHP-derived texts only (112, below the 150 floor); (B) RHP + final-Prospectus texts; (C) Plan B, download RHPs ourselves.
**Decision:** B (approved by Akshat). Use RHP- and Prospectus-derived texts; record `doc_kind` (`rhp` | `prospectus`) per text, exclude `drhp` and `unknown`. That is about 398 usable texts. When one IPO has both kinds, both stay in the same train/dev split (split by IPO, never by document) and the corpus stats say so. Counts per kind go into `eval_results/corpus_stats.json` (P1.5). Plan B is needed only if usable texts fall below 150.
**Consequences:** Prospectus texts have the offer price and rupee amounts filled in, RHP texts often show `[●]`; weak-label seeds must therefore be read per document kind (`offer_price` stays rules-only, ADR-023 note). Files are classified by cover text, not file name. Only Excel columns on an allow-list are ever summarised or sampled.

### ADR-032 LLM memory and thinking policy — proposed (30 Sep 2026)
**Context:** first measurement on the laptop: with the model unloaded RAM was 10.2 of 15.4 GB; with `qwen3.5:2b` loaded 12.0 GB (Ollama ≈ 1.8 GB). Ollama reported 3.0 GB at context 4096, split 37 % CPU / 63 % GPU, so part of the model ran on the CPU. Thinking mode was on by default and made answers very slow.
**Decision:** thinking is always disabled (`think: false`, tested). `dev_light` uses `qwen3.5:0.8b`. For `full`, the LLM must fit fully on the GPU: prefer a text-only GGUF and the smallest context that holds 5 passages, chosen from measurements in P3.1/P3.2.
**Consequences:** the 2B/4B choice waits for the bake-off; the 02 section 12 budget uses measured numbers; the live demo closes other apps.

### ADR-033 Passage ids include the document for Prospectus passages — accepted (Akshat, 30 Sep 2026)
**Context:** 02 section 9 defines `passage_id` as `<ipo_id>:p<page_start>:c<k>`. With two documents per IPO (ADR-023) page 12 of the RHP and page 12 of the Prospectus would get the same id.
**Decision:** RHP passages keep the documented format; Prospectus passages are `<ipo_id>:prospectus:p<page>:c<k>` (`core/ids.py`, round-trip tested).
**Consequences:** no existing id changes. 02 section 9 needs one line describing the Prospectus form; 02 section 9 now carries that line.

### ADR-034 Normalizer conventions — proposed (30 Sep 2026)
**Context:** P1.4 had to fix several behaviours that the docs leave open; each changes what the verifier calls ✅ or ❌.
**Decision:** (1) An amount needs a signal (currency, scale word, %, bps or a share unit); bare numbers are read only when a whole table cell is the number, with the table's unit header. (2) A scale word without a currency is rupees ("4,720 million"). (3) Equality rounds both sides to the coarser *granularity* (printed decimals × scale), so "₹ 5 crore" equals "₹ 4.6 crore" but a 10× gap never rounds away. (4) Percent: within 0.05 pp or the coarser printed precision; bps are stored as percentage points with `is_bps`. (5) "from ₹ X to ₹ Y" is two amounts (a change), not a range; a range needs low ≤ high. (6) A "-" cell is not zero; serial numbers ("1.") are not amounts. (7) `value_inr` of USD money holds the dollar amount (currency says which); USD and INR are never equal. (8) Period names use the fiscal year's ending year (FY2024-25 = 2025).
**Consequences:** the verifier (P3.3) and candidate selection (P2) inherit these rules through `normalize.equal`; extraction must pick value columns in tables (an S.No. "1" under "₹ in million" would read as ₹ 1 million).

### ADR-017 Table extractor: Docling primary, PyMuPDF fallback — proposed (30 Sep 2026)
**Context:** many RHPs draw ruling lines only around the header of the Objects-of-the-Offer table; the body rows ("Gross Proceeds … 4,720") are plain text. Bake-off on 3 RHP pages (`scripts/table_bakeoff.py`, `eval_results/table_bakeoff.json`): on Urban Company p163 (unruled body) PyMuPDF and pdfplumber found only the 2 header rows (0 value cells), Docling found both tables with 5 value cells; on the fully ruled Meesho p210 and Tata Capital p145 all three found the same value cells (3 and 61). Warm Docling on the RTX 2050 took 0.7–2.1 s/page; PyMuPDF 0.1–0.3 s; pdfplumber 0.5–1.0 s and it added spurious one-column fragments.
**Options:** (A) pdfplumber — no gain over PyMuPDF, slower. (B) PyMuPDF `find_tables` — fast, already installed, misses unruled bodies. (C) Docling — recovers unruled tables; pulls torch and ~100 packages. (D) own word-geometry heuristic — more code to maintain for what C already does.
**Decision:** Docling is the primary backend, installed only in the opt-in `tables` dependency group (`uv run --group tables …`); PyMuPDF is the automatic fallback when Docling is absent (CI, `dev_light`). Only the_offer, capital_structure and objects_of_the_offer are processed, capped at 40 pages per section. The unit header ("₹ in million") comes from the table's first two rows or the text within 72 pt above it.
**Consequences:** the offline build needs the GPU for tables (demo set: 1,000 key-section pages, 1,502 s; one process per IPO, because a single 20-document process died silently after 12); CI tests use the PyMuPDF backend and a slow test covers Docling. pdfplumber stays only for the bake-off script. Pure-OFS IPOs are recognised from the Objects text ("will not receive any proceeds from the Offer") and reported as `not_in_document`.

### ADR-035 Gold v1 is AI-prefilled, then human-verified — proposed (1 Oct 2026)
**Context:** 05 section 2 asked for blind hand labelling of 110 values (11 fields × 10 IPOs × 2 documents). Akshat instead had Claude (chat) pre-fill `gold_prefill.jsonl` from the PDFs and checked it. The file used `doc: "pro"`, `"purpose :: amount"` strings, upper-case quotes, footnote marks, `[•]`, and kept a page and quote on pure-OFS `not_in_document` rows.
**Decision:** accept the prefill as gold v1 with `label_source = "ai_assisted_verified"` on every row and the `[AI-prefilled…]` note tag removed. `gold import-prefill` fixes only the format (`pro` → `prospectus`, pairs, label_source); it never edits values or quotes. The validator now ignores case and footnote marks (`^ * # † ‡`, `(1)` after a word) when matching a value to its quote, treats `[•]` like `[●]`, checks text, list and table items as words in order (names wrap across table lines, contact details sit between list items), and lets `not_in_document` rows keep page and quote. Money, count and range values still need an exact match.
**Consequences:** the ladder and verifier numbers are scored against AI-read, human-verified labels. Reports say so (05 section 2 rule 5) and the self-consistency re-label (rule 4) is still done by hand. The hand corrections Akshat made are unrecorded.

### ADR-036 Rules extractor: boilerplate patterns, known-name lists, dev-only tuning — proposed (1 Oct 2026)
**Context:** P2.1 needs Rung 1 of the ladder. Cover pages follow SEBI wording, but BRLM and registrar tables interleave contact details and wrap names across lines, and the Objects table picked by P1.3 (first table with "proceeds") is the gross-to-net bridge, not the list of purposes.
**Decision:** (1) One regex rule per field on whitespace-squashed page text; the first hit per page, cover pages (1-15) score 0.95 down by 0.02 per page, section pages 0.7; money goes through `normalize.parse_amount`, so `[●]` is a Placeholder. (2) BRLMs and registrars are matched against short lists of known Indian firms and returned in full legal form (a wrapped "Morgan Stanley India Company Private" still yields "... Private Limited"); an unknown registrar falls back to "Capitalised Words ... Limited" at half weight; an unknown BRLM is not found (QA rungs cover it). The BRLM table is merged across a page break. (3) `objects_of_offer` is read by `extract/table.py`: among the section's tables pick the one with a general-corporate row, then "Net Proceeds" in its header, then most purpose words; serial-number columns and footnote marks are dropped; pure-OFS documents return nothing. (4) Rules were written and checked against the 3 dev IPOs only (33/33 gold values agree); test IPOs are first scored in P2.6, so their coverage numbers in `eval_results/rules_candidates.json` say a candidate exists, not that it is right.
**Consequences:** rules are fast and explainable but brittle to unknown firms and unusual wording; that is the point of the ladder. The known-name lists need updating when a new BRLM or registrar appears. Gold v1 is AI-prefilled (ADR-035), so "33/33" means agreement with AI-read, human-checked values.

### ADR-037 Pretrained QA by hand, selection rules and X-Ray semantics — proposed (1 Oct 2026)
**Context:** P2.2 needs Rung 2 (pretrained QA), a way to choose one value per field, and the X-Ray JSON. transformers 5.17 (installed with the `ml` group) no longer ships the `question-answering` pipeline (`pipeline("question-answering")` raises "Unknown task"), and a first selection rule that compared the top candidate of every extractor flagged about 90% of fields as disagreeing, because a general-purpose QA model returns plausible but unrelated spans (a face value of ₹200,000 from another page, a person's name for the registrar).
**Decision:** (1) `extract/qa_pretrained.py` runs `deepset/deberta-v3-base-squad2` with `AutoModelForQuestionAnswering` on the GPU in fp16: 384-token windows with stride 128, best start x end span, compared with the "no answer" score of the first token (SQuAD 2.0 reading); answers are cut from at most 150 passages per field (1,500 characters, sentence ends, ADR-033 ids); bare numbers take their unit and rupee sign from the surrounding text; footnote marks are dropped. (2) Selection: the field's primary extractor wins, its fallback stands in; another extractor confirms the value when any of its candidates equals it, and contradicts it only when it read a different value on the same page; a different value from another page is ignored. Names agree when one contains the other, lists when one set contains the other. A `[●]` chosen value is always reported as `placeholder` (with the other document's real value in the reason). A pure offer for sale makes `fresh_issue_size` and `objects_of_offer` `not_in_document` (verified) whatever a model guessed. Verdict `verified` means "read from the page and not contradicted", not "checked against an independent source". (3) `verify/consistency.py`: fresh issue + offer for sale = total within the coarsest printed unit; a blank or missing value is `unverifiable` (`placeholder` / `not_found`), a real mismatch is `contradicted` (`wrong_value`) and is shown in the field's `checks`; it does not change the field verdict. Derived shares of the issue are computed when all three amounts are real. (4) `xray.json` is the core `XRay` (chosen + all candidates from both documents); the UI derives the companion value from the candidates of the other document, so the schema needs no change.
**Consequences:** QA is offline only (`uv run --group ml --group tables python -m finsight.pipeline build-all --stage qa`, about 8 minutes for 20 documents); the X-Ray builds without it. Rung 2 and Rung 3 will be scored against gold in P2.6, not here.

### ADR-038 Weak-label seeds, propagation and split — proposed (1 Oct 2026)
**Context:** P2.3 turns the 389-IPO corpus (2009-2023; 110 RHP, 279 Prospectus texts) into SQuAD 2.0 training data for the ladder fields. The P2.1 rules were written for 2025 covers; older covers say "public issue", "RS 6150 LAKHS", draw ₹ as a backtick and lose the ● in [●].
**Decision:** (1) Seeds come from the rules on cover pages 1-15, only when all real cover hits agree, none is a half-weight guess, fresh + OFS = total holds when all three exist, and the dataset's allow-listed Excel columns (Total Issue Size, Fresh Issue, Offer for Sale, Face Value) agree where filled; promoter lists are trusted only in the all-capitals cover line. Rules were widened for older wording (plural lakhs/crores, "public issue", "lead manager to the issue", 15 older BRLM and 6 older registrar names); dev IPOs still 33/33. Corpus text is cleaned before use: backtick before a number -> ₹, empty brackets -> [●]. (2) Propagation: passages (1,500 characters, the field's sections) that hold the same value by `normalize.equal`, with the metric word within 250 characters before or 120 after; names by fuzzy word-order match (case, punctuation, Ltd == Limited); a list is one span covering all names, at most 700 characters; at most 8 positives per field and document. (3) Negatives: 1-2 per positive, same sections, value absent, `random.Random("<ipo>:<field>:2026")`. (4) Split by IPO, 10 % dev, seed 2026; demo and gold-v2 companies are skipped on read and asserted absent before writing. (5) Audit: 50 positives, a floor of 6 per field then proportional, seed 2026, never overwritten without `--force-audit`.
**Consequences:** 302 IPOs give 1,869 positives and 2,791 negatives (train 272 IPOs / 4,155 examples, dev 30 / 505). Seed coverage is 25-66 % per field; where the Excel has a value it disagreed with 71 total-issue, 23 OFS-amount, 19 OFS-share, 14 fresh-issue and 4 face-value seeds, which were dropped, so seed precision is not assumed: Akshat's audit (P2.4) measures it. Face value is about half the positives (short, repeated sentence); the notebook may down-weight it. BRLM, registrar and promoter seeds have no Excel check.


### ADR-039 Fine-tuning notebook design and the Kaggle hand-off — proposed (1 Oct 2026)
**Context:** P2.4 prepares Rung 3 (fine-tuned DeBERTa-v3-base-squad2). Training happens only on Kaggle, run by Akshat; the free T4 can lose a session at any time, and `datasets`/pipelines differ between transformers versions.
**Decision:** (1) One notebook with a tagged `parameters` cell (model, seeds 13/42/2026, `SLICE`, epochs 3, lr 2e-5, effective batch 16, 384 tokens / stride 128). (2) Plain `torch` Dataset plus `Trainer`, no `datasets` dependency; windows without the answer point at token 0 (the "no answer" label SQuAD 2.0 uses). (3) Checkpoint every epoch and resume; a finished seed is skipped on re-run; a NaN loss or fp16 error retries the seed in fp32. (4) The notebook carries its own EM/F1 scorer, a copy of `evaluate/metrics.py`, and a test asserts the two agree. (5) `SLICE=200` uses `train_200.jsonl`/`dev_200.jsonl` (answerable and unanswerable kept in proportion) as the smoke run that must print `SMOKE OK` before the full run. (6) Output per seed: `final/` weights and `metrics-<seed>.json`; overall `metrics.json` with mean and std. The dataset is private on Kaggle.
**Consequences:** the notebook is only structurally tested here (no outputs, cells parse, parameters present, scorer parity); its first real execution is Akshat's smoke run, so bugs surface there. Dev metrics are on weak labels: they show learning, not gold accuracy (that is P2.6 on gold v1).


### ADR-040 Retrieval design and measured memory — proposed (1 Oct 2026)
**Context:** P3.1 builds the online search path. 02 section 12 had planning estimates only; the roadmap asks for measured RAM/VRAM and a dev-only abstain threshold. The question sets (05 section 8) are Akshat's hand-work and do not exist yet, so E6 cannot run.
**Decision:** (1) ~350-token passages cut at sentence ends within a page; a table is one passage (never split), its words removed from the prose; ids per ADR-033; word boxes kept. (2) BM25 (`bm25s`) is rebuilt from `chunks.jsonl` at load (no index file); numbers are tokenised without commas. (3) Dense search is exact (one matrix product over float16-stored vectors), not FAISS: an IPO has about 3,000-5,600 passages, so an ANN index adds a dependency and recall loss for no speed gain. (4) bge-m3 (CLS, fp16 on GPU) for offline vectors and queries; ONNX int8 for CPU deploy is not built yet. (5) RRF k=60, rerank top 20 with bge-reranker-v2-m3, any failure falls back to the fused order; abstain thresholds are per method and tuned on dev only. (6) E6 counts a hit when a top-5 passage covers the evidence page or states the gold answer (at least 4 characters).

### ADR-044 Verifier rules as built: metric cues, unit slips, and what "verified" means — accepted (1 Oct 2026)
**Context:** P3.3 implements `02` section 10.3 and ADR-027. Real cover pages and the 2b model's Hindi answers forced four choices that the sketch did not settle. The rules were tuned on the 3 dev IPOs, then run once on all 10.
**Decision:** (1) **Metric of an amount** (`verify/metrics.py`), strongest cue first: a defined term right after it (`₹ 29,808 MILLION (THE "OFFER")`); else the nearest keyword before it in the same sentence, up to 320 characters, because legal prose names the metric first; a per-share keyword (face value, "at a price of", premium, price band) names only the next amount; else a keyword within 40 characters after it. An amount may carry two metrics (a pure offer for sale total is also the OFS amount). Keywords cover English, Hindi and Hinglish. (2) **Verified** = an evidence amount is equal within printed precision and nothing says it belongs to another metric; when the passages state no other value for the claimed metric, an equal value is accepted even under another keyword, to keep false alarms low. **wrong_metric** needs both: the value under a different metric *and* another value for the claimed metric. (3) **scale_mismatch** extends ADR-027: identical printed digits with a different or missing unit count for any power of ten up to 10^9 and do not need a metric match (the 2b model drops "million" in Hindi answers); different digits need different scale words, a gap of 10, 100 or 1,000 and a compatible metric. The gap is tested within printed precision ("₹ 5,421.2 lakh" against "₹ 54,211.87 million"), but a side with fewer than three significant digits must match exactly. (4) Share counts compare at printed precision ("1.11 crore shares" = 11,051,746 shares), unlike `normalize.equal`, which stays exact. (5) `normalize` now reads "मिलियन" and "बिलियन". (6) Passages cited by the sentence are searched first, so the evidence shown is the cited one. Score = verified numbers / numbers; no numbers = no score.
**E5 (unit-level benchmark, `eval_results/verifier.json`):** 45 gold values of 10 IPOs stated by a real passage (2 total-issue values skipped: no single passage on the gold page states them), templated EN/HI answers, 100 corrupted + 100 correct. **Headline, held-out (rules frozen on the 3 dev IPOs, first run on all 10): scale-mismatch recall 35/40 = 87.5 % (Wilson 73.9-94.5 %)**; dev 13/13, test IPOs 22/27; detection 100/100, false alarms 0/100 (0-3.7 %), exact reason 95/100. The five misses were rounded "crore figure printed as lakh" items on test IPOs, flagged as `wrong_value`: still ❌, with the wrong reason. **After one rule fix** (the power-of-ten test made precision-aware, decision 3) the same items score 40/40 (Wilson 91.2-100 %), exact reason 100/100, false alarms 0/100. That fix was made after seeing test-IPO misses, so 40/40 is not a held-out number and is never quoted alone. **Reporting rule:** `verifier.json` carries both in a `headline` block (`held_out`, `after_one_rule_fix`, with labels); the report and the Model Lab show 35/40 as the result and 40/40 beside it as "after one rule fix"; `metrics`, `by_split` and `by_language` in the file are the current rules. The 35/40 is a recorded constant in `evaluate/seeded_errors.py` (`HELD_OUT`), because today's code cannot reproduce the first run. The PRD target of 95 % scale-mismatch recall is therefore **not met** on the held-out run (87.5 %); the miss is explained here, as the P3.3 done-rule allows.
**Consequences:** E5 is a unit-level benchmark: it shows the rules do what they say on clean, templated answers; it does not show accuracy on free LLM text. Known gaps: when retrieval misses the cover passage a correct answer gets ⚠️ (`placeholder` or `not_found`), never ✅; a swapped metric passes as ✅ if the passages never state the claimed metric. E7 (real answers) and E9 measure these.
**Accepted by Akshat on 1 Oct 2026.** `02` section 10.3 now states decision (3): identical digits with a different or missing unit are a `scale_mismatch` for any power of ten. The rest of 10.3 is unchanged; where it is less specific than this ADR (keyword window, table cells), this ADR describes the code.
**Addendum, table cells as evidence (1 Oct, #48, `verify/table_evidence.py`):** the first build skipped bare numbers, so an answer taken from the Objects-of-the-Offer table could only get ⚠️ `not_found`. A table passage starts with `[Table, <header_scale>]`, the unit that `parse.tables` stored in tables.json. (7) Each cell is now parsed on its own with `parse_amount(cell, header_scale)`: "9,272" under "₹ in million" is ₹ 9,272 million, "(1,234)" is negative, `[●]` stays a placeholder. Guards, each with a test: bare cells are read only when the header has a scale word (184 of the 760 table passages of the 10 demo IPOs; the 574 under a plain "₹" header are capital-structure tables that mix rupees and share counts, and stay unread); the number must follow a label cell in its row (serial numbers are skipped); a bare year is a column heading; a row whose label states its own unit ("per share", "%", "(in ₹)", "number of", "ratio") is skipped; the metric of a cell comes from its own row label only. A bare cell can be a `scale_mismatch` only against a number with three or more printed digits whose metric is not per-share, so a price of ₹ 400 is not "a unit slip" of a 400 in a table. The reason text shows the unit: "9,272 (₹ in million)". Tests use the real objects tables of Ather (RHP p. 172) and Urban Company (RHP p. 164), stored as passages in `data/samples/table_passages.jsonl`. E5 is unchanged by this (same counts on a re-run). **Still open:** rows are matched by value, not by label, so "₹ 7,500 million for marketing" passes when 7,500 is the R&D row (the swapped-metric gap above); and retrieval, not the verifier, now limits the objects answer: for "How will Ather use the money raised in the IPO?" neither the `dev_light` nor the `full` profile returns the p. 172 table in the top 5 (a question that names the objects does). That goes to the chat-quality fixes.

### ADR-045 Names are compared ignoring case, punctuation and spacing — proposed (1 Oct 2026)

The first run is kept in `eval_results/ladder_strict_metric/` and under `strict_metric` in `ladder_table.json`; `05` section 4 now states the rule.
**Consequences:** test NVM changed only through names: rules 0.839 to 0.857 (promoters 0.71 to 0.86), fine-tuned 0.720 to 0.738 (promoters 0.86 to 1.00), pretrained unchanged at 0.357; the paired difference fine-tuned minus pretrained moved from +0.363 [0.214, 0.500] to +0.381 [0.226, 0.524], fine-tuned minus rules is unchanged at -0.119 [-0.214, -0.012] on the full document. ### ADR-046 Keyword guard for advice, forecasts and privacy; AI-drafted eval sets disclosed — proposed (1 Oct 2026)
**Context:** P3.4 (FR-07). FinSight must never tell anyone to apply, rate or compare IPOs, or predict listing gains, prices or profits (PRD section 9), and the Hindi bake-off showed two failures the guard must catch before any model runs: an invented "next year's profit" and a director's residential address read out of the document. The guard decides on the question alone, with no model call.
**Decision:** (1) `guard/advice.py`: regex rules for English, Hindi and Hinglish in seven kinds of request (decision, forecast, rating, comparison, strategy, GMP, personal). Hindi spelling is normalised first (nukta dropped, chandrabindu as anusvara). A GMP question is a fact only when it asks what the term means ("what does GMP mean", "GMP ka matlab"); a how-to question ("मैं आवेदन कैसे करूँ", "UPI se apply kaise karu") is procedural and passes; questions that merely sound evaluative (pending litigation, risk factors, restated profit, minimum shares to apply for) pass. (2) `guard/privacy.py`: refuses a person's home address, personal phone or e-mail, and identity numbers (Aadhaar, PAN, passport) when the question names a person or a private contact; business contacts the document prints (registered office, registrar, lead managers, compliance officer) are answered. (3) `check_question` runs privacy first, then advice. (4) `guard/facts.py`: refusal copy in English and Hindi ("Here's what the prospectus says", no nudge either way, plus a plain note that FinSight is not a SEBI-registered adviser) and `facts_payload(xray, fields, language)`, the key X-Ray fields with value, page and verdict; the guard depends on `core` only, so the caller passes the field registry. (5) API: the `guard` event's `reason` is `advice_intent` for advice, forecasts, ratings and picks (as in `06`) and `privacy` for personal details; **`06` lists only `advice_intent`, so adding `privacy` is a proposed edit to 06 for Akshat's approval**.
**E8 keyword row (`eval_results/guard.json`, `python -m finsight.evaluate.guard_eval`):** advice blocked 60/60 (Wilson 94.0-100 %), factual blocked 0/60 (0-6.0 %); English 28/28 and 0/28, Hinglish 17/17 and 0/17, Hindi 15/15 and 0/15. PRD targets (at least 95 % blocked, at most 5 % false blocks) are met **in-sample**. **Both numbers are in-sample and the set is AI-drafted:** the 60 + 60 questions in `data/gold/advice_guard_set.csv` were drafted by Claude chat (`label_source = ai_drafted_claude_chat`), 0 of 120 rows are marked reviewed by Akshat, and the rules were tuned after reading the set (first pass 49/60 blocked, 0 false blocks; misses were generalised into category rules, not phrase patches). The only unseen estimate is 85 fresh probes written after the rules and scored once before any change: **33/36 advice probes blocked (91.7 %), 0/49 factual probes blocked**; the three misses ("I should subscribe", plural "investors", "two demat accounts") were then fixed, so those probes are now regression tests in `tests/guard/test_advice.py`. Privacy probes (11 blocked, 10 business contacts passed) were written knowing the rule set and test regressions more than generalisation. 05 section 2 asks for a set written by Akshat and friends; until he reviews or replaces it, E8 reports a rule-based guard checked on drafted questions, with a likely 90 % rather than 100 % block rate on unseen wording.
**AI-drafted evaluation data, disclosed (item 4 of the P2-P3 brief):** `data/gold/questions_dev.jsonl` (20), `questions_test.jsonl` (67) and `advice_guard_set.csv` (60 advice + 60 factual) were drafted by Claude chat and are `label_source = ai_drafted_claude_chat`; the question files carry `review_status: pending` and the advice CSV has an empty `reviewed_by_akshat` column. Thresholds are tuned on the dev questions only (E6, E7); any result on them is reported as measured on AI-drafted questions until Akshat reviews them. The MuRIL classifier row of E8 would split the same set 70/15/15.
**Consequences:** the guard is cheap, explainable and testable, and will over-block some unusual factual questions and miss some unusual advice questions; the false-block risk is the one users notice, so the refusal always shows the X-Ray facts. A trained classifier (FR-18) is the planned improvement and needs a larger, independently written set. The Hindi refusal copy is neutral in gender and has not been read by Akshat yet. Forecast questions ("next year's profit") are refused here, so the generation prompt does not need to handle them; the other chat-quality fixes (citation loops, cover-page indexing, person names, exact units) belong to the chat step.

### ADR-047 Chat-quality fixes: cover-page retrieval, output guards, three-model bake-off — proposed (1 Oct 2026)
**Context:** the Hindi bake-off and dev probes showed (a) cover-page facts (registrar, lead managers, promoters, issue size, face value) missed because a title block ranks poorly against body text, (b) the RHP outranking the Prospectus for the offer price although the RHP prints a placeholder, (c) small models looping on `[1][1][1]`, answering with citations only, pasting a passage back, writing names in Devanagari and dropping units.
**Decision:** (1) `retrieve/boost.py`: when the question names a cover fact (EN/HI/Hinglish cue regexes), up to 4 passages of pages 1-3 join the candidate pool before the reranker (BM25-only: the first two lead); for price/total-issue cues Prospectus passages are placed ahead of RHP ones. (2) `generate/postprocess.py`: `LoopDetector` stops the stream on a repeating tail; `clean_answer` trims repeated sentences or citation runs and replaces empty, citation-only and pasted-passage output (at least 60 % of 8-word runs verbatim from one passage, 20+ words) with the "not found" sentence. (4) Prompt rules: copy the unit with every number, answer in own words in one to three sentences, never paste passage text, keep person and company names in Latin script in Hindi. **E6 on dev (17 answerable, AI-drafted questions), before to after:** BM25 recall@5 0.41 to 0.71, hybrid 0.41 to 0.53, hybrid+rerank 0.47 to 0.59 (MRR 0.29 to 0.33; recall@1 stays 0.18, the cross-encoder still prefers body text over the cover).
**E6 on test (56 answerable, one run, AI-drafted questions, `eval_results/retrieval.json`):** recall@5 / MRR: bm25 0.625 / 0.394, dense 0.518 / 0.347, hybrid 0.643 / 0.436, hybrid+rerank 0.607 / 0.514 (recall@1 0.464). **Bake-off re-run (28 answerable items per model, retrieval contained the gold in 26/28):** Hindi number copy: qwen3.5:4b 9/13, qwen3.5:2b 8/13, gemma4:e2b 0/13 (it returned empty output for 17 Hindi prompts, which `clean_answer` turned into "not found"; direct API calls with the same options answered, cause not found); English qwen3.5:4b 10/13, 2b and gemma 9/13 (a first run of the same script gave 2b 6/13 Hindi and 10/13 English: sampling at temperature 0.2 moves a 13-item score by two or three). Median answer time: 2b 5.6 s, gemma 3.0 s, 4b 9.6 s on the RTX 2050 (4B partly offloaded to CPU). The unanswerable probes (home address, next year's profit) are now refused by the guard before the model runs. Loop trims (Hindi): 2b 2, 4b 0 in the second run. **ADR-020 is not changed:** it waits for Akshat's fluency ratings in `data/gold/hindi_fluency_sheet.csv` (new `auto_correct` column pre-filled from the gold value, not hand-written).
**Consequences:** cover questions are answerable again; the reranker is the weak stage and a cover-aware score is a Phase 5 candidate; thresholds and the 4B latency are open items for the API RAM plan.

### ADR-048 Privacy in three layers: one guarded path, redaction at indexing, an output filter — accepted (1 Oct 2026; `privacy` guard reason approved by Akshat)
**Context:** the rated Hindi bake-off sheet showed a 4B model reading out a CEO's residential address (and a 2B/4B pair giving a promoter's and a CEO's addresses in Devanagari). Two causes: the bake-off called the model directly and bypassed the guard, and the RHP/Prospectus print every director's and KMP's residential address, which sat in the search index. The question guard (ADR-046) alone cannot stop a model that volunteers an address under an unrelated question.
**Decision:** (1) **One path.** `generate/respond.py` is the only code that streams from a model: question guard, retrieval, prompt, generation, output rules, privacy output filter. The `ask` CLI and the bake-off use it; the chat orchestrator (P3.6) and through it the API must. `tests/generate/test_single_path.py` fails if any other module in `src/` or `scripts/` calls a backend. (2) **Redaction at indexing** (`retrieve/redact.py`, applied in `retrieve/chunk.py`): address columns of director tables are blanked; prose after "residential/permanent/current address", a bare "Address:" in a passage that also holds DIN/date of birth/occupation, or "is residing at" is replaced by `[withheld for privacy]`; board tables that the table stage reads as flowing prose are cut by word position (the address column, from the header or from the "DIN: …" rows on a continuation page, down to the first left-column line after the last DIN). Registered-office, registrar, lead-manager, bank and company-promoter addresses are kept. The PDF and word boxes are untouched: it is the public document and "Show in document" still opens it; what changes is what a model can retrieve and repeat. (3) **Output filter** (`guard.check_output`): an answer with a house/flat/sector detail, a person-plus-address statement (EN/HI), a phone number, an e-mail or a PAN/Aadhaar-like number is replaced by the privacy refusal; a business context (registered office, registrar, compliance officer) lets address-like text through, but never an identity number. 06: the guard event's `reason` is `advice_intent | privacy`.
**Evidence:** `scripts/privacy_scan.py` over the 10 rebuilt indexes (`uv run python scripts/privacy_scan.py`): passages with a residential-address cue after redaction 0 for 5 IPOs and 2 for 5 IPOs, all ten being "Registration Number … Address" / registered-office lines of the company; the three leaked addresses are gone from the index; no DIN is followed by an address except for corporate promoters and BRLM/legal-counsel offices. Tests: `tests/retrieve/test_redact.py` (prose, tables, geometry, continuation pages, idempotence, span alignment), `tests/guard/test_privacy_output.py`, `tests/generate/test_respond.py` (a leaked address from a fake model is blocked and kept only in `raw`). Test addresses are invented.
**Consequences:** this is detection by patterns and page geometry, tuned on the layouts of the 10 demo IPOs; a new layout can leak, so the three layers overlap on purpose and the scan is re-run after every re-index. Redaction changes passage boundaries, so indexes must be rebuilt (`build-all --stage index --dense`, about 20 minutes for 10 IPOs). Streamed tokens are not vetted: UIs show them as a draft until `Response.text` (the 06 `answer` event) replaces them. A person named in the answer text who has a public registered address is not covered beyond the patterns above.

### ADR-049 The reranker stays; precision and truncation are not the problem; abstaining on retrieval score is weak — accepted (2 Oct 2026)
**Context:** E6 on test (ADR-047, 56 answerable, AI-drafted questions) had hybrid+rerank below hybrid on recall@5 (0.607 vs 0.643) although it ranked better (recall@1 0.464 vs 0.339, MRR 0.514 vs 0.436). Akshat asked for fp32 vs int8 ONNX, truncation and input order to be checked, and for the abstain threshold to be tuned on a larger dev set. **Dev only: `questions_test.jsonl` was not opened** (`retrieve.evaluate --dev-only`, `scripts/rerank_experiment.py`; AI-drafted questions, 41 answerable and 9 unanswerable on the 3 dev IPOs, redacted index of ADR-048).
**Reranker variants on the same hybrid candidate pool (`eval_results/rerank_dev.json`, recall@5 / recall@1 / MRR, seconds per question for 20 passages):** hybrid without reranker 0.561 / 0.317 / 0.399 (0 s); fp16 torch on the GPU, 512 tokens 0.561 / 0.342 / 0.411 (0.8 s); fp32 torch 0.561 / 0.342 / 0.411 (3.5 s); fp32, 1,024 tokens 0.561 / 0.342 / 0.409 (3.5 s); question and passage swapped 0.488 / 0.317 / 0.381 (the shipped order is right); ONNX fp32 on CPU 0.561 / 0.342 / 0.411 (41.6 s); **ONNX int8 on CPU 0.537 / 0.317 / 0.389 (26.1 s)**. In the first 10 questions' pools, 27 of 232 passages (11.6 %) exceed 512 tokens, yet 1,024 tokens changes nothing, so truncation does not explain the loss. A dev re-run of the `hybrid+rerank` row of `retrieve.evaluate` differs from the experiment by one question (0.317 vs 0.342 at recall@1) because query vectors were embedded in different batches: differences of one question are noise at n = 41.
**Decision:** (1) Keep bge-reranker-v2-m3 in fp16 on the GPU for `full`; precision (fp16 = fp32) and length (512 = 1,024) are not the cause of the test difference, which was 2 of 56 questions at recall@5 and is smaller than the gain at recall@1. (2) int8 ONNX loses one question of 41 and is too slow on CPU for a 20-passage pool (26 s; a pool of 10 would still be ~13 s), so `deploy_cpu` does not get a reranker from this experiment: ADR-022 stays open and BM25 (recall@5 0.61 on dev, the best single method) is the deploy fallback. ONNX export is kept only in the experiment script (`onnx` dependency group). (3) **Abstain thresholds** (`eval_results/retrieval_dev.json`): balanced-accuracy tuning refuses 15 of 41 answerable dev questions for hybrid+rerank (threshold 0.459; 8 of 9 unanswerable caught; leave-one-IPO-out 7/9 and 16/41) and nothing for hybrid, which is unusable; so the rule is now "the highest threshold that refuses at most 10 % of answerable dev questions": hybrid+rerank -4.402 (in-sample 2/9 unanswerable caught, 4/41 wrongly refused; leave-one-IPO-out 3/9 and 7/41), hybrid and BM25 never abstain on score (any threshold that catches an unanswerable question refuses more than 10 % of answerable ones), dense 0.468 (0/9, 4/41). `configs/config.yaml` `full` carries only the hybrid+rerank value in `retrieve.abstain_thresholds`.
**Consequences:** retrieval score is a weak abstain signal here (best honest figure: about a third of unanswerable questions caught at a 17 % false-refusal rate when the threshold is tuned on other IPOs), so "not found" rests on the model's own answer plus the verifier; the chat must not describe the abstain event as a safety guarantee. Dev set is AI-drafted, 50 questions on 3 IPOs, and was also used to choose the cover-page cues (ADR-047): every dev number is in-sample for that part. Test numbers were not refreshed and keep ADR-047's caveats. A cover-aware reranking (Phase 5) remains the lead for recall@1 on cover facts.

**Context:** Run 1 found that no candidate carried a box (the API matched text on every request), that the popover rebuilt each fact's sentence in the browser, that the thumbnail strip downloaded full pages, and that the lab heatmap had numbers but no examples (spec 8.2).
**Decision:** (1) `extract.fill_boxes` stores each candidate's box (+ its existing doc and page) when the X-Ray is built; the API prefers it and only falls back to text matching for older X-Rays (`locate_bbox` moved from `api` to `extract`). (2) `XRayField.sentence = {text, hit}` from `extract.sentence_around`, the same tight-band logic the browser used, 10 words each side. (3) `GET /pages/{n}?w=` returns a WebP scaled to `w` pixels (40-1200, never enlarged, cached in memory); the strip asks for 160. (4) `ladder_table.json` gains `examples_test` (up to 5 test rows per rung, field and setting; misses first); the numbers in the file did not change (checked against the committed file).
(5) `XRay.bid_closed = {closed_on, page}` read from the Prospectus cover by `extract.find_bid_closed` ("BID/OFFER CLOSED ON ...", with the variants the ten prospectuses print: no ON, the typo CLOSEED, a comma after the month); the API sends it on the X-Ray and the workspace header shows "Bid closed {date} (Prospectus p. {n})". All ten dates were found; each listing date in `ipo_meta.yaml` is that date plus three working days.
**Consequences:** `openapi.json` and `frontend/lib/api/types.ts` regenerated; 06 updated; the X-Rays must be rebuilt (`pipeline build --stage xray`) to carry stored boxes. Examples are the first result file of a rung (seed 13 for the fine-tuned rung), not an average.

### ADR-054 addendum (2 Oct 2026, bug fix) — the X-Ray route no longer opens the parsed documents
**Bug.** With the real API, opening any IPO from the Library showed an error. The X-Ray route rebuilt each fact's source sentence (and, for values the build found no box for, tried to find one) from the parsed documents: two files of about 70 MB, about 2.5 s of CPU each to validate, holding the GIL. For 5 to 9 s every other request, `/api/health` included, waited; uvicorn's 5 s keep-alive closed the sockets the Next dev proxy held, which answered 500 ("socket hang up", ECONNRESET), and React Query's single retry failed the same way. It hid in the run-2 checks because later requests hit the cache and the first load is racy.
**Fix.** `Candidate.sentence` and `sentence_hit` are stored with the box at build time (`fill_boxes`); `XRay.boxes_located` says the build already looked, so a value without a box is not searched for again; the API serves both without opening a document (X-Ray request: 5.3 s to 0.02 s; a burst of 12 requests on a cold API: 6 s to 0.1 s). An older X-Ray (no flag) still takes the slow path, so nothing breaks before a rebuild. `poe api` also gets `--timeout-keep-alive 30`. **Existing X-Rays must be rebuilt:** `uv run python -m finsight.pipeline build --ipo <id> --stage xray` for each IPO.
**Tests.** `tests/api/test_xray_cold.py` (the parsed loader raises if called), and `frontend/e2e/workspaces-real.spec.ts` (`E2E_REAL=1`, real API) opens every IPO from the Library and fails on a failed `/api` request, an error block, a page error or an X-Ray slower than 3 s; it fails on the old code (5.1 s).

### ADR-022 Deployment target: Space (Docker, CPU) plus Vercel, BM25 and a 4-bit GGUF — proposed (2 Oct 2026; needs Akshat review)
**Context:** the public demo has no GPU. ADR-049 measured BM25 recall@5 0.61 on dev and int8 ONNX reranking at 26 s per 20-passage pool on CPU, too slow to ship. Scripted questions are covered by the recorded demo cache.
**Decision:** (1) API in a Docker Space on the free CPU tier (`Dockerfile`, `deploy/space/`), profile `deploy_cpu`, demo mode on. (2) Retrieval is BM25 only: the image sets `FINSIGHT_RETRIEVE__RERANK=false` (the YAML keeps `rerank: true`, which needs torch). (3) LLM through llama-cpp-python (`generate/llama_cpp_backend.py`, same contract as the Ollama backend; `get_llm` picks it from `llm.backend`) with `Qwen3.5-2B-Q4_K_M.gguf` from the Hub, the 4-bit file of the model measured on the laptop. (4) Data comes from `scripts/bundle_artifacts.py` (X-Rays, parsed text, sections, BM25 chunks, page images, demo cache, eval results; no PDFs, no dense index). (5) Website on Vercel; `/api/*` is rewritten to the Space, so no CORS rule.
**Consequences:** the deployed model's answer quality is **not measured** (quantised file, BM25 only, no reranker): run E7 against it before quoting a number for the deployed system. Live answers on a shared CPU take tens of seconds and may hit the Vercel proxy time limit; the fix, if needed, is a CORS rule and a direct browser call (D7). Voice is off. Nothing was deployed or tested in a container in this run unless `docs/MORNING_REPORT.md` says so.
**Phase 2 note (3 Oct 2026):** superseded **as the primary deployment** by B-ADR-04 (Google Cloud Run CPU API + CPU job + optional L4 GPU job, Supabase, GCS, Vercel). Kept as a **paid, optional** showcase-only fallback (B07 cut 6, profile `deploy_cpu`): free HF accounts can no longer create Docker CPU Spaces, so it needs HF PRO.
